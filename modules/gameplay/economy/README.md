# 货币与奖励：经济系统第一版

状态：实验性 C++17 实现。提供多货币钱包、混合奖励、购买事务、成功请求去重，以及完整经济快照的存档与恢复。不是完整 MMO 后端，也不是数值平衡模型。

构建目标：`designer::economy`，公开依赖 `designer::inventory`，不依赖 Godot 或文件适配器。

## 模型与职责

| 类型 | 职责 |
| --- | --- |
| `CurrencyCatalog` | 不可变货币定义，非零 ID 与正数余额上限 |
| `Wallet` | 自有规则及余额，增加、扣除、快照恢复 |
| `Cost` | 本次需要扣除的货币列表 |
| `RewardBundle` | 本次发放的货币与普通堆叠物品 |
| `Transaction` | 非零请求 ID、目标容器 ID、成本与奖励 |
| `Receipt` | 规范化请求与成功序号 |
| `Economy` | 玩家钱包、容器、成功请求记录的所有者与执行器 |

`CurrencyId` / `ContainerId` 使用 uint32，`Amount` / `RequestId` 使用 uint64。金额只使用整数，若有小数就选择最小单位。初版不包含负债、浮点金额、汇率、物品成本、装备实例或真实支付验单。

钱包中没有记录的货币余额为零；读取未知 ID 也返回零，但所有修改都拒绝未知货币。持久化的余额记录必须为正数，零余额不保存。货币定义与余额分离，不把客户端传入的 ID 或价格当授权依据。

## 钱包规则

- `credit` / `debit` 拒绝零金额和未知货币。
- 增加先检查 `amount <= max_balance - balance`，避免先相加产生溢出。
- 扣除先检查余额，不允许负数。
- 每个失败操作保持原余额不变。
- `restore` 使用当前规则检查所有余额，再复制候选并提交。余额超新上限时拒绝，不静默截断。

独立 Wallet 可用于建模与初始化。经济状态接管钱包后，对外只提供只读视图，正常业务修改经由 `execute`。

## 交易流程

```text
检查输入长度和合法性
  → 同类条目合并、检查溢出、按 ID 升序规范化
  → 检查同请求 ID 的成功记录
  → 检查记录上限及目标容器
  → 复制整个候选状态
  → 扣除全部成本
  → 发放全部货币奖励
  → 发放全部物品奖励
  → 准备回执、记录及返回结果
  → 用 unique_ptr::swap 统一提交
```

只有最后一步修改正式状态；此前业务失败或分配异常都丢弃候选状态。回执和返回对象的分配也在提交前完成，编译期检查返回对象可无异常移动。

### 明确的业务语义

- 全部成功或全部不变，不支持部分购买或部分领奖。
- 先付成本再收奖励，不能用本笔奖励为本笔成本垫付。
- 同币成本和奖励分别验证，不通过净额绕过余额要求。
- 奖励货币超上限时整笔失败，不裁剪、丢弃或转成邮件。
- 目标容器放不下或不认识奖励物品时，钱包和历史记录也不变。
- 空成本允许免费奖励；空奖励允许纯扣款；两者都为空时拒绝。
- 所有请求都指定一个已存在目标容器，包括纯货币请求，以保持契约一致。
- 成本只支持货币；物品消耗、促销限制、购买资格和税费后续按场景扩展。

输入中同种货币或物品可以分成多个条目，例如药水 2+3 与药水 5 被规范化为相同请求。三种列表分别限制原始长度，超限请求即使合并后很短也拒绝。

## 重复请求与回执

- 新 ID：尝试执行，成功后保存规范化内容和连续成功序号。
- 同 ID、同规范化内容：返回原回执，`replayed=true`，不修改任何资产。
- 同 ID、不同内容：返回 `request_conflict`。
- 失败请求不占用记录或序号，同 ID 同内容在条件改变后可以重试。
- 记录已满时拒绝新交易，但仍允许查询/重放已成功的请求。

去重边界是当前 Economy 对象及恢复到其中的历史。请求 ID 由可信调用方分配，不能把会循环重置的计数当跨会话全局 ID。此记录不是完整审计账本：没有记录失败操作、可信时间、来源授权或完整余额变化。

**请求去重不等于只能领取一次。** 更换请求 ID 仍是新请求。任务、邮件以后必须把自身的领取状态与发奖一起纳入提交，不能只调用免费奖励来实现一次性领取。

本模块是可信领域内核：示例直接构造成本和奖励。联网时客户端只能传商品等业务意图，服务端查规则并校验资格，不能让客户端任意构造奖励包。

## 状态所有权与扩展边界

`Economy` 以值拥有钱包、容器和规则，统一提交后，旧的 `wallet()` 引用、`container()` 指针及槽位引用会失效。需要保留状态时使用快照；不要跨修改操作缓存只读视图。对象不允许隐式复制；显式 `clone()` 创建含规则、资产、记录及容量限制的独立副本，用于外层候选协调。所有访问按单线程处理，未提供锁或并发保证。

当前聚合只执行购买、发奖、纯扣款命令。已有宝箱/仓库转移仍可在独立 inventory 示例使用；若要在此聚合内部转移，需要后续新增命令并纳入协调器，不应暴露可写指针绕过提交边界。`restore` 是加载入口，不作为普通玩法修改捷径。

候选复制包括所有容器、规则与成功历史，易于验证但成本随状态和历史增长。此版没有性能预算或压测结论，不适合直接宣称满足 MMO 负载。以后可以测量后优化不可变规则共享与候选变更集，但保持对外事务语义。

## 统一存档与恢复

`economy/archive.hpp` 提供 `encode_archive` / `decode_archive`。它们只处理内存字节，不直接访问磁盘；文件保存复用 `designer::persistence`。

一份快照包含：

1. 钱包余额。
2. 按稳定 ID 标识的所有容器（包括仓库）。
3. 所有成功请求与回执，按序号 1、2、3……排列。

`restore` 在候选状态中依次检查钱包、容器集合/规则、规范化回执、序号、重复 ID 和回执引用的当前规则，再统一提交。任何一步失败都不改原状态。历史奖励在空目标容器上验证，检查当前配置是否仍支持这些物品及容量；配置变化可能要求未来迁移。

历史不是从初始状态重放得到的，也没有签名；恢复无法证明资金来源或验证全部历史余额轨迹。加载更旧的合法存档会回到更旧的资产和去重记录，当前不提供防存档回滚或防篡改机制。

### 格式版本 1

固定小端编码：

```text
magic = ASCII DECOARCH (8 bytes)
version: uint32 = 1
balance_count: uint32
  repeated: currency_id uint32, amount uint64（ID 严格升序）
container_archive_size: uint32
container_archive: bytes（现有 DINVARCH v1，含其完整校验）
receipt_count: uint32
  repeated:
    sequence uint64, request_id uint64, destination uint32
    cost_count uint32; repeated currency_id uint32, amount uint64
    currency_reward_count uint32; repeated currency_id uint32, amount uint64
    item_reward_count uint32; repeated item_id uint32, quantity uint32
checksum: uint64 = FNV-1a of all preceding bytes
```

编码及解码只在成功时替换输出。拒绝截断、尾部垃圾、重复/不规范条目、非法计数、校验损坏和未来版本。FNV-1a 仅检查意外损坏，不是密码学认证。

这个新格式不覆盖原 DINVARCH 格式。原有纯容器存档仍由 inventory 解码，但不会自动转换为含钱包的经济存档；没有旧经济版本，暂未实现迁移器。

### 资源与保留限制

- 货币定义/余额：最多 1024 种。
- 每笔成本货币、奖励货币、奖励物品：各最多 64 个原始条目。
- 记录数：默认 256，可配置为 1–4096；达到上限拒绝新请求，不清除旧记录。
- 容器及格数：沿用 inventory 的 128 容器、单容器 100000 格、总计 200000 格。
- 编码文件最多 16 MiB；以上上限使可提交的正常状态保持在此范围内。

记录保留策略不能永远依赖拒绝新交易。后续上线需设计持久化请求表、会话/序列号或明确重试窗口，不能随意删历史后仍承诺永久去重。

保存仍与内存提交分开。保存失败时应保留未保存状态并重试保存，不能重新执行购买。恢复到最后一份完整快照可保持资产和记录一致，但尚未持久化的成功交易可能在崩溃后丢失；服务端可靠确认需要数据库事务或持久化日志。

## 示例

```cpp
namespace eco = designer::economy;
namespace inv = designer::inventory;
eco::Wallet wallet(eco::CurrencyCatalog({{1, 1000}}));
const auto funded = wallet.credit(1, 500); // 可信初始化；调用方检查错误。
eco::Economy player(std::move(wallet), {
    {1, inv::Inventory(20, inv::ItemCatalog({{1001, 20}}))}
});
const auto result = player.execute({42, 1, {{{1, 100}}}, {{}, {{1001, 5}}}});
// 只有 result.error == Error::none 才成功；再次执行同请求返回原回执。
```

运行（第一条替换指定示例文件，第二条只加载）：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/examples/designer_economy_example build/example-economy.sav
./build/examples/designer_economy_example build/example-economy.sav --load
```

示例结果为金币 500 → 400，积分 90 → 95，获得药水 5。容量不足的另一笔购买不扣款，成功请求重复执行及独立进程加载后重放都不重复发奖。

## 验证

测试覆盖钱包边界与 uint64 最大值、10000 次钱包操作、多项奖励失败原子性、合并溢出、请求冲突、失败后同请求重试、日志满后重放、统一恢复校验、500 次模型对照交易、2000 次格式变异、逐分配点 bad_alloc 注入，以及独立进程保存和恢复去重。

商业级剩余工作包括可信来源校验、一次性业务领取状态、并发与数据库持久性、记录保留、配置迁移、性能预算和发布平台验证。质量要求见 [工程质量要求](../../../docs/quality.md)。
