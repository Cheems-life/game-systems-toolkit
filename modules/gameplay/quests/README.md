# 任务与目标：第一版需求

状态：需求与接口方向设计中，尚无任务实现。采用独立于 Godot 的 C++17，具体公开 API 和存档格式待设计。

## 职责与范围

管理任务定义、目标进度、开启条件、状态流转与一次性领奖。核心不认识怪物、NPC、物品交互或场景节点。玩法层确认事实，适配层将其转换为目标更新，任务核心维护进度及状态。

第一版包含：最低等级条件、累计计数与永久达成标记、多目标全部达成、可信事件批量更新、一次性奖励、必要的去重和统一存档。

不包含：前置任务条件、日常重置、分支、放弃/失败/超时、可回退状态目标、任意达成、分阶段、世界修改、编辑器或 UI。扩展方向见下文，预留契约不代表已经实现能力。

## 定义、状态与冻结

- 任务定义：非零 ID、配置版本、展示描述、最低等级、目标列表、奖励。
- 目标定义：任务内独立 ID、目标类型及其规则版本；描述文本不参与判定。
- 已接状态：冻结目标/奖励，记录各目标进度、领奖和必要去重信息。
- 状态：未解锁 → 可接取 → 进行中 → 可领奖 → 已领奖；前两项由条件计算。

已接任务的目标与奖励不随商品式配置更新而改变。只有已接、尚未领奖的任务可以推进；任务一次性，不允许重复接取重置进度。当前条件改为等级，因此任务 A 领奖不会自动解锁任务 B；B 是否可接由自身最低等级决定。

## 开启条件：等级求值

当前仅支持“玩家当前等级 >= 任务最低等级”，两者均应为有效正数。最低等级配置在任务定义中；当前等级由可信的只读玩家上下文提供。任务不负责经验、升级或保存第二份可变等级。

接口方向：`evaluate(ConditionSpec, PlayerReadContext) -> ConditionResult`，不是已经实现的 C++ API。

结果契约：

| 情况 | allowed | 原因与错误 |
| --- | --- | --- |
| 满足 | true | 原因 none，求值无错误 |
| 等级不足 | false | 原因 level_too_low，参数包含 required / actual，求值无错误 |
| 上下文无效、规则未知等 | false | 独立的求值错误，不伪装成正常等级不足 |

原因码稳定、可测试，显示文案由表现层本地化。未来等级/世界标记/时间组合仍调用同一个求值入口；第一版不实现组合表达式，但不把具体条件分支写入任务状态机。

查询与实际接取均求值，接取以当次可信上下文为准。接取之后等级降低不取消任务，也不阻止目标推进和领奖。客户端不能通过提交一个任意等级取得资格。

## 目标类型与处理器扩展

第一版两个目标：

- 累计计数：正数增量，达到目标值封顶，不回退。
- 永久达成标记：由未达成变为达成，重复设置无额外效果。

预留 `ObjectiveTypeId → ObjectiveHandler` 注册边界。处理器负责配置/状态校验、对候选进度应用更新，以及读取是否达成；注册与查找不依赖具体玩法类。第一版只装配上述两类，暂不提供插件系统。

注册规则：重复类型拒绝，配置/恢复遇到未知类型或不兼容版本时失败并保留现有状态；装配后规则固定。处理器不得产生外部副作用或绕过候选状态修改正式数据。配置和状态表示必须容纳类型及规则版本，具体 C++ 参数载体仍待设计。

目标组合另设边界，第一版固定全部达成。未来“任意达成”改变组合判定，“分阶段”还需目标激活和推进顺序；仅增加叶子目标处理器不足以自动支持它们。不现在构建通用目标树。

“当前持有若干物品”属于可回退状态条件，不能偷换成累计获得；此类目标后续另行设计。

## 事件与进度

- 事件由可信玩法/适配层产生，不接受客户端任意改进度。
- 接取前行为不补算；接入与核心事件协议需明确有效时间/顺序，防止旧事件被当新事件。
- 一个事件可推进多个任务和目标，重复事件不重复计数。
- 多项更新整体成功或整体不变；计数封顶，标记幂等。
- 去重状态随存档保存；事件 ID 范围、冲突、容量及保留策略在实现前明确，不能静默淘汰后继续宣称永久去重。

具体事件载荷与处理器接口尚待设计，不建立击杀专用核心字段。

## 领奖：可扩展准备阶段，统一提交

目标全部达成后可领奖。流程方向：

```text
校验领奖资格 / 请求重放
  → 建立结算计划及统一玩家候选状态
  → 准备资产奖励
  → 准备任务已领奖状态
  → 准备成功请求回执
  → （未来：准备世界状态修改）
  → 准备返回结果
  → 一次统一提交
```

计划条目或准备阶段可扩展，第一版只包含现有资产、任务与回执内容，不实现任意事务插件框架。任何阶段的错误、分配失败均丢弃候选，保持原资产和任务不变；不能让各阶段分别提交或直接调用数据库、网络与场景修改。

同一成功请求重试返回原结果；更换请求 ID 也不能再次领取已领奖任务。奖励超限或背包不足时整笔失败，任务仍为可领奖。

未来若引入世界标记，它与任务/资产进入同一候选、同一存档边界；场景表现读取已提交状态。可靠外部事件投递需未来另行设计，不把提交后普通回调当可靠机制。

## 玩家状态与持久化

商城与任务必须操作同一份玩家经济资产，不创建两份钱包。共同协调者的具体实现尚待设计，第一版实现时要先解决现有商城所有权与任务接入的协调。

存档统一覆盖资产、任务冻结规则和进度、领奖状态、事件与领奖去重记录；恢复全部验证后一次提交。等级的权威值和持久化属于玩家/成长状态，任务只消费可信上下文。

以上均指设计目标，当前没有任务序列化或迁移实现；单线程候选提交不等于数据库事务或并发原子操作。

## 实现验收计划

- 等级低于、等于、高于门槛；无效上下文；查询后等级变化及接取时重查。
- 已接任务不因降级取消，多目标计数/标记全部达成才可领奖。
- 注册重复或未知类型/规则版本时明确失败，不静默跳过目标。
- 重复事件、批量失败、数量边界，失败不修改进度或消耗去重记录。
- 领奖失败仍可重试，换请求 ID 和重启都不能重复发奖。
- 配置更新不改变已接目标与奖励，统一存档失败或恢复失败不留下部分状态。
- 结算准备阶段失败不影响真实资产/任务；未来世界状态阶段遵守同一边界。
