# 背包与物品

状态：实验性。第一版 C++17 领域实现已完成，本机规则验证通过；尚未完成商业级性能、平台或联网验收。

## 范围

固定格数、同类物品堆叠，提供添加、按物品移除、格间移动与整格交换。独立于 Godot、core、存储和网络。

不包含重量、格子形状、装备词条、实例身份、绑定、过期、使用效果、自动排序、跨容器交易或持久化。不可堆叠不等于拥有唯一身份。线上重复请求仍会重复执行，幂等性由后续请求/事务层设计。

## 数据模型

| 类型 | 字段 / 内容 | 意义 |
| --- | --- | --- |
| `ItemDefinition` | `id`, `max_stack` | 固定物品规则 |
| `ItemCatalog` | 按 ID 查询的规则集合 | 构造时验证，运行时不更新 |
| `ItemStack` | `item_id`, `quantity` | 某格持有状态 |
| `Slot` | `optional<ItemStack>` | 空格或非空物品堆 |
| `Inventory` | 自有规则副本、固定大小槽位数组 | 维护规则、封装修改 |

ID 与数量都是 `uint32_t`。ID 0 保留为无效 ID；有效定义必须有正数堆叠上限，重复 ID 拒绝。空规则集合和零格背包合法。

定义与持有状态分离，名称、图标等不进入背包领域数据。若以后支持带词条的装备，需要定义实例身份及堆叠兼容条件，不能仅根据物品类型 ID 合并。

## 必须成立的规则

- 格数创建后不变，槽位下标从 0 开始。
- 每个非空槽位引用已知物品，数量在 `[1, max_stack]` 内。
- 数量归零时槽位必须清空，不保留零数量堆。
- `add` 成功只增加请求的数量；`remove` 成功只减少请求的数量。
- 移动和交换保持每种物品的总数量不变。
- 所有返回业务错误的操作均保持整个背包不变。
- 通过公开 API 修改，不对外提供可写槽位。

## 操作契约

| 操作 | 成功规则 | 失败情况 |
| --- | --- | --- |
| `add(item, quantity)` | 先填同类已有堆，再填空格；两者分别按下标升序 | 零数量、未知物品、整体容量不足 |
| `remove(item, quantity)` | 按下标升序扣除；零数量堆清空 | 零数量、未知物品、总数量不足 |
| `move(source, destination, quantity)` | 空目标拆堆，同类目标合并；合法原地移动不改变状态 | 零数量、越界、空来源、来源数量不足、目标异类、目标容量不足 |
| `swap_slots(first, second)` | 整格交换，可交换空格；原地交换不改变状态 | 越界 |

不支持部分成功。例如添加 30 个但只剩 20 个空间时，不会先放入 20 个。调用方若需要部分拾取，应另行定义带实际数量的接口，不能偷偷改变现有契约。

多种错误同时存在时，检查顺序固定：添加/移除先数量、再物品、再容量或持有量；移动先数量、下标、来源、持有量、原地、目标类型、目标容量；交换只检查下标。

## 原子性如何实现

添加和移除分两阶段：只读预检查确认完整请求可执行，然后提交。固定槽位数组、简单值类型且无外部回调，使提交阶段无需分配内存或执行外部逻辑。容量检查逐步减少剩余需求，避免把所有槽位容量累加进 `uint32_t` 导致溢出；合并先比较剩余空间再加数量。

移动检查所有条件后才修改两个槽位。当前没有观察者回调或线程并发，所以不会暴露中间状态。

这种原子性仅覆盖一次内存操作。跨背包交易、商店扣费、保存到数据库不能依赖它获得事务保证。未来接入事件与持久化时必须重新验证提交边界。

## 错误、所有权与线程

正常业务失败返回 `Error`，调用方用 `error_name` 获取诊断文本。构造时非法配置抛出 `invalid_argument`；内存分配失败保留标准异常语义。

背包以值方式拥有规则副本，避免外部规则变化使已有物品堆失效。传入左值会复制规则，传入临时值或 `std::move` 可转移所有权。

`slots()` 返回只读引用，不是独立快照。需要比较操作前后状态时使用 `auto before = bag.slots()` 复制；引用不能超过背包生命周期。当前没有并发保证，所有访问需在同一线程或由外部同步。

## 使用

CMake 目标：`designer::inventory`，头文件：`designer/inventory/inventory.hpp`。

```cpp
namespace inv = designer::inventory;
inv::Inventory bag(20, inv::ItemCatalog({{1001, 20}, {2001, 1}}));
const auto result = bag.add(1001, 25);
if (result != inv::Error::none) {
    // 处理业务失败，背包保持原状态。
}
```

运行 [命令行示例](../../../examples/inventory/main.cpp)：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/examples/designer_inventory_example
```

## 验证与成本

边界测试覆盖非法规则、未知物品、零数量、零格背包、容量及持有量不足、拆堆、合并、整堆移动、交换、原地操作、越界和最大整数数量。另外用固定随机种子执行 10000 次连续操作，以独立数量模型和状态快照检查不变量。

添加/移除时间复杂度为 O(槽位数)；移动/交换的槽位操作为 O(1)，规则哈希查询为平均 O(1)。内存为 O(槽位数 + 规则数)，每个背包持有规则副本。当前没有实测性能预算，不承诺 MMO 规模表现。大规模部署时再测量规则副本成本，必要时使用明确所有权的共享不可变规则。

商业级完成定义仍见 [质量要求](../../../docs/quality.md)。后续优先接存档，再设计奖励事务、唯一物品实例和可信端请求层。
