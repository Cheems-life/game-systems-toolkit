# 背包与物品

状态：实验性。C++17 领域实现及快照/跨容器扩展已完成，本机规则验证通过；尚未完成商业级性能、平台或联网验收。

## 范围

固定格数、同类物品堆叠，提供添加、按物品移除、格间移动与整格交换。独立于 Godot、core、存储和网络。

不包含重量、格子形状、装备词条、实例身份、绑定、过期、使用效果、自动排序、跨玩家交易、数据库事务或云持久化。不可堆叠不等于拥有唯一身份。线上重复请求仍会重复执行，幂等性由后续请求/事务层设计。

## 数据模型

| 类型 | 字段 / 内容 | 意义 |
| --- | --- | --- |
| `ItemDefinition` | `id`, `max_stack` | 固定物品规则 |
| `ItemCatalog` | 按 ID 查询的规则集合 | 构造时验证，运行时不更新 |
| `ItemStack` | `item_id`, `quantity` | 某格持有状态 |
| `Slot` | `optional<ItemStack>` | 空格或非空物品堆 |
| `Inventory` | 自有规则副本、固定大小槽位数组 | 维护规则、封装修改 |

ID 与数量都是 `uint32_t`。ID 0 保留为无效 ID；有效定义必须有正数堆叠上限，重复 ID 拒绝。空规则集合和零格背包合法。

定义与持有状态分离，名称、图标等不进入背包领域数据。若以后支持带词条的装备，需要定义实例身份及堆叠兼容条件，不能仅根据物品类型 ID 合并。

## 必须成立的规则

- 格数创建后不变，槽位下标从 0 开始。
- 每个非空槽位引用已知物品，数量在 `[1, max_stack]` 内。
- 数量归零时槽位必须清空，不保留零数量堆。
- `add` 成功只增加请求的数量；`remove` 成功只减少请求的数量。
- 移动和交换保持每种物品的总数量不变。
- 所有返回业务错误的操作均保持整个背包不变。
- 通过公开 API 修改，不对外提供可写槽位。

## 操作契约

| 操作 | 成功规则 | 失败情况 |
| --- | --- | --- |
| `add(item, quantity)` | 先填同类已有堆，再填空格；两者分别按下标升序 | 零数量、未知物品、整体容量不足 |
| `remove(item, quantity)` | 按下标升序扣除；零数量堆清空 | 零数量、未知物品、总数量不足 |
| `move(source, destination, quantity)` | 空目标拆堆，同类目标合并；合法原地移动不改变状态 | 零数量、越界、空来源、来源数量不足、目标异类、目标容量不足 |
| `swap_slots(first, second)` | 整格交换，可交换空格；原地交换不改变状态 | 越界 |

不支持部分成功。例如添加 30 个但只剩 20 个空间时，不会先放入 20 个。调用方若需要部分拾取，应另行定义带实际数量的接口，不能偷偷改变现有契约。

多种错误同时存在时，检查顺序固定：添加/移除先数量、再物品、再容量或持有量；移动先数量、下标、来源、持有量、原地、目标类型、目标容量；交换只检查下标。

## 原子性如何实现

添加和移除分两阶段：只读预检查确认完整请求可执行，然后提交。固定槽位数组、简单值类型且无外部回调，使提交阶段无需分配内存或执行外部逻辑。容量检查逐步减少剩余需求，避免把所有槽位容量累加进 `uint32_t` 导致溢出；合并先比较剩余空间再加数量。

移动检查所有条件后才修改两个槽位。当前没有观察者回调或线程并发，所以不会暴露中间状态。

上述单容器操作只覆盖自身状态；跨背包转移的扩展见下文。商店扣费、保存到数据库不能依赖这些操作获得跨模块事务保证。未来接入事件与持久化时必须重新验证提交边界。

## 错误、所有权与线程

正常业务失败返回 `Error`，调用方用 `error_name` 获取诊断文本。构造时非法配置抛出 `invalid_argument`；内存分配失败保留标准异常语义。

背包以值方式拥有规则副本，避免外部规则变化使已有物品堆失效。传入左值会复制规则，传入临时值或 `std::move` 可转移所有权。

`slots()` 返回只读引用，不是独立快照。需要比较操作前后状态时使用 `auto before = bag.slots()` 复制；引用不能超过背包生命周期。当前没有并发保证，所有访问需在同一线程或由外部同步。

## 使用

CMake 目标：`designer::inventory`，头文件：`designer/inventory/inventory.hpp`。

```cpp
namespace inv = designer::inventory;
inv::Inventory bag(20, inv::ItemCatalog({{1001, 20}, {2001, 1}}));
const auto result = bag.add(1001, 25);
if (result != inv::Error::none) {
    // 处理业务失败，背包保持原状态。
}
```

运行 [命令行示例](../../../examples/inventory/main.cpp)：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/examples/designer_inventory_example
```

## 验证与成本

边界测试覆盖非法规则、未知物品、零数量、零格背包、容量及持有量不足、拆堆、合并、整堆移动、交换、原地操作、越界和最大整数数量。另外用固定随机种子执行 10000 次连续操作，以独立数量模型和状态快照检查不变量。

添加/移除时间复杂度为 O(槽位数)；移动/交换的槽位操作为 O(1)，规则哈希查询为平均 O(1)。内存为 O(槽位数 + 规则数)，每个背包持有规则副本。当前没有实测性能预算，不承诺 MMO 规模表现。大规模部署时再测量规则副本成本，必要时使用明确所有权的共享不可变规则。

商业级完成定义仍见 [质量要求](../../../docs/quality.md)。已扩展本地存档和跨容器转移；后续设计奖励事务、唯一物品实例和可信端请求层。

## 跨容器转移

宝箱、背包与仓库都是 `Inventory`；权限、距离、宝箱生成/刷新规则位于调用方。本地示例没有 MMO 身份、权限和多人抢夺逻辑。

- `source.transfer_to(target, item, quantity)`：按来源槽位顺序扣除，目标先填同类堆再填空格。
- `source.transfer_all_to(target)`：按来源槽位顺序把全部物品放入目标；空来源成功且不改变状态。
- 来源与目标为同一对象时返回 `same_container`，不会把转移变成原地重排。
- 目标可以有不同堆叠上限：按目标规则重新分堆。目标不认识物品时失败。
- 全部拾取若任何一种物品放不下，双方都不变，不提供隐式部分拾取。

按数量转移复制来源和目标为候选容器（包含规则副本），在候选中移除及添加；全部拾取复制目标并准备空来源槽位。所有分配和检查完成后，用槽位 vector 的 swap 提交，不调用外部回调。异常同样不会修改原始容器。

该实现便于理解，但有复制与分配成本：按数量转移为 O(双方格数 + 双方规则数)；全部转移重复调用添加，最坏为 O(来源格数 × 目标格数 + 目标规则数)。没有并发访问时，两次不抛异常的 swap 之间不会被观察到。并发访问需外部同步；这不是数据库事务或无锁并发算法。

## 快照与恢复

`snapshot()` 返回拥有自身数据的槽位副本。`restore(snapshot)` 验证格数、物品是否已定义和每堆数量，再复制候选并提交。失败不修改原对象，也不自动扩容、裁剪、丢弃未知物品或改变堆叠布局。

`Inventory::restore_many(requests)` 对所有目标验证并暂存后再提交，拒绝空指针或重复目标。支持快照引用当前槽位，因为会先复制所有候选数据。输入空列表合法。

规则更新后，原存档超出新堆叠上限时恢复失败；需要未来迁移策略来决定重新分堆或发补偿，不能静默删除超量物品。

## 多容器存档格式

公开头文件：`designer/inventory/archive.hpp`。

`Archive` 是多份 `ContainerSnapshot` 的集合，每份保存非零 `ContainerId` 和槽位。ID 由调用方稳定分配，与数组顺序无关。示例固定使用 1=背包、2=仓库、3=宝箱；真实项目需明确身份映射，不能把临时内存地址当 ID。

```text
magic       8 bytes: ASCII DINVARCH
version     uint32: 1
containers  uint32
repeat containers:
  id        uint32
  slots     uint32
  repeat slots:
    tag     uint8: 0=空格，1=物品堆
    if tag=1:
      item  uint32
      count uint32
checksum    uint64: preceding bytes 的 FNV-1a
```

所有多字节整数固定使用小端编码，不保存 C++ 对象原始内存。当前仅支持版本 1，未来版本返回 `unsupported_version`；还没有真实旧版本，也未编写迁移器。库版本与存档格式版本分开管理。规则配置不写入文件，使用当前规则验证；后续需评估配置版本迁移。

解析限制：16 MiB、最多 128 个容器、单容器最多 100000 格、合计最多 200000 格。拒绝重复/零容器 ID、非法标签、零物品 ID/数量、截断、尾部垃圾和校验不匹配。解码器只验证结构；物品是否存在和数量是否超过上限在恢复阶段验证。

`encode_archive` / `decode_archive` 只在成功时替换输出。`restore_archive` 要求存档与绑定的 ID 集合完全匹配，每个 ID 对应一个不同的非空对象，再调用统一恢复。返回值同时提供存档错误和底层背包错误。

FNV-1a 只用于意外损坏检测，有碰撞且能被修改者重新计算，不是认证、加密或防作弊机制。配置升级、内容删除、扩容等迁移仍需真实场景驱动设计。

## 一致保存与运行示例

相关容器进入同一份 Archive，编码后交给独立的 `designer::persistence` 文件适配器。这样不会出现保存新背包却仍保存旧仓库的两个文件版本；恢复也统一提交。

```sh
./build/examples/designer_inventory_storage_demo build/example-player.sav
./build/examples/designer_inventory_storage_demo build/example-player.sav --load
```

第一条执行拾取、存入、取出并替换指定示例文件；第二条只从上一次进程保存的文件恢复。不要把示例路径指向需要保留的真实存档。

第一次保存后的内存转移不会自动触发磁盘保存；调用方负责持久化时机。保存失败不回滚已成功的内存转移。共享世界宝箱或多个玩家资产不能仅靠此单份本地存档处理，需要服务端事务。

新增测试覆盖双容器失败原子性、目标规则差异、整箱拾取、多容器恢复失败与输入别名、5000 次连续转移、截断/损坏/非法格式与 3000 次解析变异、文件往返和独立进程恢复。
