## 场景与问题

不能在写新存档时先截断唯一有效旧存档；还需区分替换成功与持久性不确定。

## 数据、接口与关键规则

同目录 mkstemp → 完整写入 → 文件 fsync → close → rename → 目录 fsync；RAII 清理未提交临时文件。返回 committed 区分是否已替换正式路径。

## 为什么这样设计与替代方案

直接覆盖旧文件会在中断时损坏唯一版本。同目录临时文件便于进行原子替换；目录同步失败发生在 rename 之后，此时报告 durability_uncertain 且 committed=true，不能假装旧文件仍在。

## 实现步骤与提交边界

替换前失败保留旧文件 → 替换后标记已提交 → 同步目录 → 返回结果。保存失败时保留未保存内存并重试保存，不重新执行购买或转移。

## 取舍、限制与后续

POSIX 保存实现，Windows 返回 unsupported_platform；无备份、云同步或数据库事务。原子替换不等于完整游戏持久化确认。
