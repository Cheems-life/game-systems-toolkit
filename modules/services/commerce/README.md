# 商城与支付：第一版游戏内商城

状态：实验性 C++17 实现。支持商品目录、上下架、多份购买、历史价格回执、请求重放和完整商城存档。**没有真实支付、内购验单、退款、库存、限购、折扣或商城 UI。**

构建目标：`designer::commerce`，公开依赖 `designer::economy`，间接依赖 inventory。文件保存另行组合 persistence，不依赖 Godot 或平台 SDK。

## 职责与模型

| 类型 | 作用 |
| --- | --- |
| `ProductDefinition` | 商品 ID、配置版本、上下架状态、单份成本与奖励 |
| `ProductCatalog` | 自有不可变商品定义，支持按 ID 查询和只读遍历 |
| `PurchaseRequest` | 请求 ID、商品 ID、份数、目标容器 ID |
| `PurchaseReceipt` | 原购买意图、当时商品版本、实际经济回执 |
| `Shop` | 持有一个玩家的经济状态和成功购买记录，协调统一提交 |

价格与奖励来自可信目录，请求不允许指定价格和奖励。货币支付、余额、背包容量及事务仍由经济模块负责。

### 配置规则

商品 ID 与版本为非零 uint32，份数为 uint32，使用经济模块的 uint64 请求 ID。最多 4096 个商品。单份成本至少有一种货币，奖励至少有一种货币或物品；不提供免费商品和无奖励商品。免费领取仍使用经济模块。

构造目录时分别排序成本、货币奖励和物品奖励，拒绝零 ID/数额、重复条目、重复商品和各列表超过 64 项的配置。结构合法不等于货币和物品存在：跨目录引用在经济执行时校验，未知内容使整笔失败。

`entries()` 返回只读 map，可按 ID 升序展示商品；调用方决定是否隐藏下架商品。名称、图标和文案不属于此领域模型。

### 多份购买

一份包含 5 瓶药水，购买 3 份就支付 3 倍单份成本并获得 15 瓶。每一项乘法先验证 `unit_amount <= max / quantity`，失败返回 `quantity_overflow`。不使用溢出后的结果，不通过浮点金额计算。

## 购买流程与原子性

```text
验证请求四个字段均非零
  → 查商城成功记录：同意图返回原回执，不同意图报冲突
  → 检查商城记录容量
  → 查商品是否存在及上架
  → 检查数量乘法并构造经济交易
  → clone 独立经济候选 + 复制商城历史
  → 在候选经济中扣款、发全部奖励、生成经济回执
  → 准备商城回执、商城记录及返回对象
  → 统一交换 Shop 的状态指针
```

如果经济层发现同请求 ID 已存在，但商城没有对应记录，无论经济交易内容相同还是不同，都返回 `request_conflict`，不把其他经济操作误认为商城订单。商城和经济操作共享同一玩家的请求 ID 命名空间，由可信调用方协调分配。

正常业务失败返回 `PurchaseResult.error`；经济失败同时带 `economy_error` 和 `inventory_error`，便于区分钱不足、背包不足等情况。配置错误在构造时抛 `invalid_argument`，内存分配失败保留标准异常。

任何前置失败与分配异常都保留原资产、经济记录和商城记录。返回对象也在提交前准备，编译期验证可无异常移动。上述提交仅为单线程内存边界，不是数据库事务。

## 重试、改价与上下架

相同购买意图指请求 ID、商品 ID、份数和目标容器 ID 都相同。成功后改价、改奖励、改版本、下架甚至移除商品，都不能改变旧请求结果。新请求才查当前商品配置。

示例：请求 42 以每份 100 金币买两份，实际支付 200。改价到 150 后，请求 42 重试仍返回原来的 200 金币交易和旧商品版本；新请求买一份支付 150。

`replace_catalog` 原子交换一个已验证的目录，调用方负责版本编号和内容发布；不自动检查版本是否递增，也不要求恢复存档时保留旧商品配置。替换不修改玩家状态。新请求若面对下架商品返回 `product_unavailable`，面对不存在商品返回 `unknown_product`。

失败请求不留成功记录，可以同 ID 同内容重试，届时按当前目录执行。该版没有报价锁定、价格确认或失败订单记录；若要保证“玩家看到的旧报价”，需要后续增加报价版本/有效期协议。现有“旧价格重放”只承诺已成功请求。

## 所有权、容量与限制

`Shop` 接管 `unique_ptr<Economy>`，不提供可写经济对象，避免外部修改破坏协调边界。调用方转移所有权后不得再使用事先保留的可写别名。可用 `Economy::clone()` 保留独立分支，但它们不是共享实时账户。

成功 purchase/restore 后，旧 economy、钱包、容器及槽位视图失效；replace_catalog 后，旧商品指针失效。跨操作保留数据应使用快照或值副本。所有访问为单线程，无多线程或多进程同步保证。

商城成功记录默认 256，配置范围 1–4096；经济记录另有自身上限。任何一层满都会拒绝新购买，已成功的商城请求仍可重放。旧记录不会静默淘汰，长期运行策略后续设计。

当前商城只提供购买命令，不暴露任意发奖、仓库转移或任务领取命令。未来这些业务应统一扩展协调边界，而非直接改只读经济状态。

候选复制包含资产、规则及双方历史；经济候选执行内部也会再次复制。这样容易验证但有明显时间与内存成本。当前没有性能测量或 MMO 负载承诺，不先引入通用事务框架。

## 存档与恢复

`Snapshot` 包含完整经济快照及按经济序号递增排列的购买回执。经济序号允许有间隔，因为接管前可能已经有非商城经济操作。

- 恢复验证购买意图、非零商品版本、唯一请求 ID、目标容器、回执序号及完整经济回执一致。
- 数额必须可以分解为正数单份数额乘份数；实际经济状态仍由经济层检查当前货币、物品和容器规则。
- 不重新查询当前商品目录，不按今天的价格重算历史。
- 全部校验、复制和记录准备完毕才统一提交；失败保留原状态。

回执关联证明快照内部一致，不证明历史配置真实。格式没有签名，不能防篡改、伪造商品来源、删除记录或回滚旧存档。商城记录可为经济记录的子集，因为历史中允许非商城交易；缺失的购买意图不能从经济记录自动推断或补造。

### DSHPARCH 版本 1

固定小端编码：

```text
magic = ASCII DSHPARCH (8 bytes)
version uint32 = 1
economy_size uint32
economy_bytes（完整 DECOARCH v1，含其校验）
purchase_count uint32
repeat purchase_count:
  request_id uint64
  product_id uint32
  quantity uint32
  destination uint32
  product_version uint32
  economic_sequence uint64
checksum uint64 = 前述字节的 FNV-1a
```

完整经济交易仅编码一次，购买记录通过请求 ID 和经济序号引用它；解码时恢复完整购买回执。文件上限 16 MiB，最多 4096 条购买记录，嵌入经济快照沿用其资源限制。

拒绝截断、尾部垃圾、非法关联、重复记录、零字段、不规范顺序、校验损坏、未来版本及超限计数。编码和解码失败或分配异常不修改输出。FNV-1a 仅检测意外损坏，不是安全认证。

这是独立商城文件格式，不改变 DECOARCH 或 DINVARCH。已有纯经济存档可先用原接口恢复到 Economy，再把对象交给 Shop，原经济记录会保留；不会自动生成历史购买意图。没有旧商城版本，因此暂未实现格式迁移器。

内存购买与文件保存仍是两个提交边界；保存失败重试保存，不能重做购买。确认可靠持久化、并发访问和真实支付必须另行设计服务端事务及平台适配。

## 运行

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/examples/designer_commerce_example build/example-commerce.sav
./build/examples/designer_commerce_example build/example-commerce.sav --load
```

首条示例替换指定示例存档，执行两份购买、改价和新购买，再保存全部状态。第二条使用空商品目录加载，并重放已成功请求。不要将路径指向需保留的真实存档。文件保存适配器目前只在 macOS 本地文件系统验证。

## 验证与后续

覆盖商品校验、多币/物品数量缩放溢出、余额/容量失败、改价/下架/移除后重放、请求冲突、双层记录上限、经济请求冲突、候选副本独立性、恢复关联、200 次模型对照购买、2000 次格式变异、逐分配点 bad_alloc，以及独立进程恢复。

当前没有限购、库存、折扣、商品刷新、退款、UI 或真实支付。后续若增加库存与限购，其状态必须与扣款发货一起提交；支付验单与平台补单不能直接用当前游戏币购买代替。商业级验收见 [质量要求](../../../docs/quality.md)。

## 与任务共享玩家资产（2026-10-18）

新增 `PurchaseBook`，只保存购买记录，不拥有资产。`prepare(catalog, const Economy&, request)` 不修改输入，成功时返回独立经济候选、购买记录候选和已准备回执；重放或失败没有可提交候选。独立 Shop 继续通过此准备入口提交，旧公开购买接口和 DSHPARCH 格式保持兼容。

任务的 `quests::Player` 也复用 PurchaseBook，并统一持有同一个 Economy、购买记录和 QuestBook，不再通过两个独立 Shop/任务对象共享可写裸指针。PurchaseBook::restore 校验记录关联，经济当前规则由其所有者在同一候选中验证。接入细节见 [开发步骤 004](development/004-independent-purchase-preparation.md)。
