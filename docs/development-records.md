# 开发记录约定

本工程以学习设计为目标。每个系统不仅记录“怎么用”，还必须逐步记录“解决什么问题、为什么这样设计、如何证明”。

## 文件组织

- `modules/<分类>/<系统>/README.md`：当前能力、使用方式、契约和限制。
- `modules/<分类>/<系统>/development/README.md`：按编号排列的步骤入口与状态。
- `modules/<分类>/<系统>/development/001-<主题>.md`：一个有意义的开发步骤或决策。
- [全系统索引](systems-development.md)：所有系统的记录入口。

“步骤”指可独立解释的设计/实现变化，例如定义模型、加入原子操作、加入持久化、修正边界；不要求每行代码单独一篇。一个步骤可由多次提交完成。跨系统变更分别记录各自职责并互相链接，共享内容引用已有文档。

## 工作顺序

1. 开始前阅读本系统 README 和已有记录。
2. 实现前建立步骤文档，记录场景、不变量、方案和取舍，状态为“设计中”。
3. 实现过程中记录接口、状态转换、失败语义、所有权和实际变更。
4. 验证后补充执行命令、环境、结果与未覆盖范围；未运行必须明确写明。
5. 完成后更新状态、系统 README 与步骤索引，与对应代码一起提交。可用提交主题或既有提交号追溯，不为写入自身哈希而反复修改提交。
6. 后续改变旧决策时新增记录，标明替代关系；旧记录保留作为历史，当前契约以更新后的系统 README 为准。

记录不以代码逐行翻译为目标，要解释规则为何成立、替代方案为何暂不采用、什么场景会使方案失效。学习中产生的重要解释可补进相关步骤文档；纯排版可在既有步骤补充维护说明，不必制造空洞新步骤。

## 每篇记录的必填内容

- 状态、日期、关联系统和代码/提交依据。
- 具体场景、范围与不做的内容。
- 数据模型、所有权、依赖、接口及必须成立的不变量。
- 关键选择、替代方案、选择理由和成本。
- 实现顺序、成功与失败路径、提交或回滚边界。
- 验证方法、执行结果和未验证范围。
- 已知限制、下一步和决策变更关系。

不涉及的项写明“不适用”并简述原因。模板见 [步骤模板](templates/development-step.md)。

## 历史与真实性

2026-10-17 首次补录现有实现。补录依据为代码、已有说明和 Git 历史，无法确认的历史理由不编造为当时结论。测试源码说明覆盖意图，实际执行结果需有执行依据；不能把本次未运行的历史测试写成刚刚通过。

未实现系统只提供入口和待办状态。公共质量要求、资源上限及商业级限制不能因为有了文档就被视为满足。
