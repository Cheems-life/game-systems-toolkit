# 工程质量要求

商业级是针对明确平台、负载和产品场景的验收结果，不是目录结构或一个统一功能清单。工具包采用按需组合的方式，避免为了通用性引入没有实际用途的抽象。

## 架构约束

- 领域规则尽量独立于引擎；引擎依赖集中在适配层。具体分层方式随技术栈确定。
- 模块的公共接口、依赖、初始化和销毁顺序必须明确，不允许循环依赖。
- 不强制采用微服务、事件总线或依赖注入框架；以真实使用场景决定。
- 本地单机与服务器权威属于不同信任模型，不承诺同一个实现直接满足两者。
- 客户端不能可靠保守秘密，也不能独自保证付费权益、在线经济和成绩可信。加密存档不等于防作弊。

## 模块发布门槛

- 有适用范围、公开接口、最小可运行示例和集成/卸载说明。
- 核心规则及高风险边界有自动化测试；涉及迁移、事务和联网的模块有相应故障验证。
- 覆盖必要的损坏数据、重复操作、中断、取消、重入和并发场景。
- 给出目标设备、负载、内存和耗时预算及测量结果，不能只宣称“高性能”。
- 维护数据/协议/配置版本；破坏性变更有迁移指南。持久化写入失败不能破坏最后有效数据。
- 日志、指标和错误能够定位故障，避免输出凭据及敏感个人数据。
- 第三方依赖与示例素材授权清楚；公开发布前确定许可证。
- 平台认证、支付、隐私及发行要求按实际发行地区和渠道核对，不把本项目文档当作合规结论。

## 仓库与交付

版本控制保存源代码、文档、必要配置与合法可分发的小型样例。生成物、缓存、凭据和真实用户数据不入库。大型二进制资产是否采用 Git LFS，待引擎及资产规模确定。

确定技术栈后配置构建、测试和 CI；依赖应锁定可复现版本。模块状态使用“设计骨架 / 开发中 / 实验性 / 可用”，升为可用需注明版本及验证证据。

## 设计过程记录

每个系统的每个有意义开发步骤必须有对应设计记录，解释为什么选择该方案、失败语义及实际验证范围。与代码同次维护，使用 [开发记录约定](development-records.md)，通过 [全系统索引](systems-development.md) 查阅。
